Summary

At a Glance

PinLearn went from a working feature demo with a single 1,199-line server file and no tests, to a layered, tested, containerised application with a CI pipeline and a consistent UX foundation.

1,199 → 40lines in server.js
1 → 40automated tests (26 backend, 14 frontend)
0 → 3CI jobs (backend, frontend, Docker)
~25 → 1error-handling code paths
4critical security holes closed
0 → 2health endpoints (liveness, readiness)

The five changes that matter most

ChangeWhy it matters in one sentence
Layered backendEach file now has one job, so logic can be tested and changed without touching HTTP code.
Zod validation + central errorsEvery input is checked at the door, and every failure comes back in the same shape with a request ID.
Server-derived streaksThe product's core metric can no longer be faked by an empty POST request.
Route guards + 401 handlingSigned-out users are redirected, and expired sessions recover cleanly instead of breaking pages.
Tests + CI + DockerEvery push is verified automatically, and anyone can run the full stack with one command.

What is still open

  • No refresh tokens or token revocation; the JWT lives for 7 days in sessionStorage.
  • Integration tests stop before the database. Signup, boards and streak flows are not tested end to end.
  • Rate limiting and the YouTube cache are in-memory, so they do not scale past one server instance.
  • Dashboard.jsx (470 lines) and Kanban.jsx (921 lines) are still large; there is no shared button or form component library.
  • Docker images were written but not built locally; CI builds them on the first push.

Project Overview

What the application does

PinLearn is a Pinterest-style learning tracker. A user signs up and picks interests (React, DSA, DevOps...). The dashboard then surfaces YouTube tutorials and GitHub repositories for those topics. Users save resources to boards, move them through saved → visited → in progress → completed, attach notes, plan work on a Kanban board, take a daily quiz, and build a streak shown on an activity calendar.

Key engineering decisions

Validate at the boundary, trust inside

Zod parses input once in middleware. Controllers read req.valid and never re-check types.

Pure functions for business rules

computeStreak() and scoreQuiz() take data and return data, so they are tested without a database.

The server derives business events

Streak days are written only after verified actions. The client can no longer claim activity.

Let the database enforce uniqueness

A unique index closes the "check then insert" race that application code alone cannot.

Fail closed in production

Empty CORS_ORIGINS rejects browsers; the self-signed TLS bypass is ignored in production.

Document known limits

The README lists what is not solved yet. Honest trade-offs read better than hidden gaps.

Complete Change Log

Every change, grouped by category. Each entry ends with a one-line talking point you can say out loud.

Architecture Changes

Split the monolith into layersbackend/{app,server}.js, config/, routes/, controllers/, services/, middleware/, validators/, utils/
Before
One 1,199-line server.js holding routing, validation, logic, API clients, caching and startup.
Now
Eight folders, each with one responsibility. server.js is ~40 lines of startup and shutdown.
Why
Code that does everything cannot be tested, reviewed or changed safely.
Benefits
Isolated unit tests, smaller diffs, obvious place for every new feature.
Recruiter impact
Removes the single biggest red flag in the original review.
Talking point
"I refactored a monolith into routes, controllers and services so business rules became pure, testable functions."
App factory separated from server startbackend/app.js, backend/server.js
Before
Importing the app connected to MongoDB and started listening.
Now
createApp() builds the app; server.js connects, listens and handles shutdown.
Why
Tests need the app without a port or a database.
Benefits
supertest drives the real middleware stack in memory.
Recruiter impact
Shows awareness of testability as a design goal.
Talking point
"Separating construction from startup is what made HTTP-level tests possible."

Backend Changes

Centralised error handlingmiddleware/errorHandler.js, utils/AppError.js
Before
~25 copy-pasted try/catch blocks; responses mixed {message} and {error}; CORS errors became HTML pages.
Now
Code throws AppError(status, message, code). One handler maps Zod, Mongoose, bad JSON, oversize body and duplicate-key errors to { message, code, details?, requestId }.
Why
Inconsistent errors make clients fragile and leak internals.
Benefits
Predictable API contract; 5xx details never reach users; every error is traceable.
Recruiter impact
Signals production thinking rather than tutorial code.
Talking point
"Express 5 forwards async errors, so handlers just throw and one middleware decides what the client sees."
Schema validation on every endpointvalidators/*.js, middleware/validate.js, config/env.js
Before
Ad hoc checks; some routes validated, some (/api/interests) did not; no length limits.
Now
Zod schemas for every body, query and param, plus the environment itself. Results land on req.valid.
Why
Untrusted input is the root of most API bugs and injection attacks.
Benefits
Type coercion blocks {"$ne": null} injection; field-level error messages; config fails fast at boot.
Recruiter impact
Matches what reviewers expect in any production Node API.
Talking point
"Validation happens once at the boundary; past that point the code can trust its inputs."
Token logic in one serviceservices/tokenService.js, middleware/authMiddleware.js
Before
JWT signing and user-response shaping duplicated in signup and login.
Now
signToken, verifyToken (algorithm pinned to HS256) and buildAuthResponse in one file.
Why
Duplicated security code drifts; pinning the algorithm blocks algorithm-confusion attacks.
Benefits
One place to add refresh tokens later.
Recruiter impact
Shows DRY applied where it matters most.
Talking point
"Auth logic lives in one service, and verification only accepts the algorithm we sign with."
Third-party integrations as servicesservices/{youtube,github,quiz}Service.js, services/providerClient.js
Before
Inline fetch code; YouTube cache never evicted; substring filter dropped "shortcuts" tutorials; API key in URL.
Now
Bounded TTL cache (500 entries) with request coalescing; whole-word filtering; keys in headers; 8-second timeouts; pure scoreQuiz().
Why
Unbounded memory growth and leaked keys are production incidents waiting to happen.
Benefits
Stable memory, fewer quota hits, testable scoring.
Recruiter impact
Demonstrates awareness of cost, quotas and failure modes.
Talking point
"Concurrent identical searches share one in-flight request, and the cache is capped so memory cannot grow forever."

Frontend Changes

Route guards and shared layoutsrc/App.jsx, routes/RequireAuth.jsx, routes/AppLayout.jsx, routes/pageRoutes.jsx
Before
Any URL rendered without a token; <Navbar/> copy-pasted into 9 routes; boards fetched on the login page.
Now
Nested routes: RequireAuth → AppLayout (Navbar + Outlet) → pages. Boards load only after login.
Why
Duplicated layout drifts, and unguarded pages show broken shells.
Benefits
One place for auth, one place for layout; fewer wasted requests.
Recruiter impact
Fixes an obvious gap any reviewer clicks into first.
Talking point
"Layout routes with Outlet let me guard and wrap every private page in one declaration."
Global 401 handlingsrc/api/client.js
Before
Expired tokens produced generic errors on each page.
Now
A 401 on an authenticated call clears the session and fires auth:session-expired; the guard redirects to login. Errors are typed ApiError with status and code.
Why
Session expiry is a cross-cutting concern; handling it per page guarantees inconsistency.
Benefits
Clean recovery; failed logins do not trigger it (tested).
Recruiter impact
Shows thinking about the whole session lifecycle.
Talking point
"The API client owns session expiry, so no page has to know about it."
Error boundary, cleanup and extractioncomponents/ErrorBoundary.jsx, hooks/useThemeClass.js, Kanban/kanbanUtils.js, package.json
Before
A render crash blanked the app; unused redux-saga and dotenv; Kanban helpers inside a 1,034-line component.
Now
ErrorBoundary fallback with reload; unused dependencies removed; Kanban helpers moved to kanbanUtils.js (921 lines remain).
Why
Blank screens lose users; dead dependencies suggest copy-paste.
Benefits
Graceful failure, smaller install, clearer component.
Recruiter impact
Removes "tutorial residue" signals.
Talking point
"Error boundaries are still class components in React; I use one at the root as the last line of defence."

Database Changes

Schema-level constraintsmodels/User.js, models/Boards.js, models/QuizCompletion.js
Before
Password selectable by default; email not normalised; unbounded strings and arrays.
Now
password: select:false; email lowercased and trimmed; max lengths everywhere; caps of 30 interests, 500 resources per board, 100 notes per resource.
Why
Defence in depth: the database should reject bad data even if a route forgets.
Benefits
No accidental password leaks; documents cannot approach Mongo's 16 MB limit.
Recruiter impact
Shows understanding of embedded-document limits.
Talking point
"Secure defaults: the password field is excluded unless a query explicitly asks for it."
Indexes and the board-name racemodels/Boards.js, controllers/boardController.js
Before
Duplicate check with a case-insensitive regex, then insert: unindexable and racy.
Now
Case-folded nameKey with a partial unique index {userId, nameKey}; duplicate-key error mapped to 409; index on {userId, createdAt}.
Why
Two parallel requests could both pass the check and both insert.
Benefits
Correct under concurrency; faster board listing.
Recruiter impact
Race conditions are a classic interview topic; this is a real example.
Talking point
"The partial index meant legacy boards without the new field could not break the migration."
Dedicated Activity modelmodels/Activity.js, services/streakService.js
Before
Non-quiz activity was stored as a fake QuizCompletion with quizId: "activity-save".
Now
Activity {userId, date, type} with a unique {userId, date} index; streak reads both collections.
Why
Overloading a model hides meaning and corrupts analytics.
Benefits
Idempotent daily writes; honest data model; backward compatible.
Recruiter impact
Shows data-modelling judgement.
Talking point
"A unique index makes 'record today's activity' idempotent without any locking."

Section 4

Interview Cheat Sheet

Short answers you can give in 30 seconds, tied to this project. Practise saying them aloud.

What is centralised error handling?
Short answerA single middleware receives every error, decides the status code and response body, and logs it. Route code just throws.
How we used itAppError(status, message, code) plus errorHandler.js, which maps Zod, Mongoose, JSON-parse and duplicate-key errors to one JSON shape with a requestId.
Why industry uses itConsistent contracts for clients, no leaked stack traces, one place to add alerting.
Follow-upsHow does Express know a middleware is an error handler? (four arguments) · What changed in Express 5 for async errors? · Operational vs programmer errors?
Why validate requests with a schema library?
Short answerA schema declares the exact shape of valid input; anything else is rejected before business logic runs.
How we used itZod schemas for every body, query and param, plus process.env. A validate() middleware puts parsed data on req.valid.
Why industry uses itPrevents injection, gives precise error messages, and doubles as documentation (and can generate OpenAPI or TypeScript types).
Follow-upsParse vs validate? · Where else should validation live (DB constraints)? · How does NoSQL injection work?
What is a service layer?
Short answerA layer that holds business rules, separate from HTTP (controllers) and storage (models).
How we used itstreakService, quizService, tokenService, youtubeService. Controllers are 5-15 lines each.
Why industry uses itLogic can be reused (CLI, queue worker, other routes) and unit-tested without HTTP.
Follow-upsService vs repository pattern? · Where would you put a transaction? · How would dependency injection help testing?
How do route guards work in React?
Short answerA wrapper route checks auth and either renders its children (<Outlet/>) or redirects with <Navigate/>.
How we used itRequireAuth wraps AppLayout, which wraps all private pages, and listens for a session-expired event.
Why industry uses itOne declaration protects many routes; layout and auth stay in sync.
Follow-upsIs a client-side guard real security? (No: the API must enforce it) · How would you preserve the intended URL after login? · Role-based guards?
What is rate limiting and how do you choose the key?
Short answerCapping requests per client per time window to prevent abuse and protect resources.
How we used itGlobal 300/15 min, auth 20/15 min, provider proxies 30/min keyed by user id; trust proxy so IPs are real behind Render.
Why industry uses itStops brute force, scraping and runaway bills on paid APIs.
Follow-upsFixed window vs sliding window vs token bucket? · Why does in-memory limiting break with two servers? · What is a 429 + Retry-After?
What is structured logging?
Short answerLogging JSON objects with fields instead of free text, so logs can be searched and aggregated.
How we used itPino with a per-request ID returned in X-Request-Id; secrets redacted; pretty output in dev only.
Why industry uses itTools like Datadog, ELK and CloudWatch query fields; request IDs connect a user's bug report to one log line.
Follow-upsLogs vs metrics vs traces? · What must never be logged? · What is log level and when do you use each?
Liveness vs readiness checks?
Short answerLiveness: "is the process alive?" Readiness: "can it serve traffic right now?"
How we used it/api/health always 200 for Render; /api/ready returns 503 when MongoDB is disconnected. Both bypass the rate limiter.
Why industry uses itOrchestrators restart dead containers and stop routing to unready ones, enabling zero-downtime deploys.
Follow-upsWhy not check the DB in liveness? (a DB outage would restart every pod) · What is graceful shutdown?
What is CI/CD?
Short answerCI automatically builds and tests every change; CD automatically deploys changes that pass.
How we used itGitHub Actions: backend tests + audit, frontend tests + build, then Docker builds. Render and Vercel deploy from main.
Why industry uses itSmall, verified, frequent changes are safer than big manual releases.
Follow-upsHow would you add a staging environment? · Branch protection? · How do you handle secrets in CI?
Why Docker, and what is a multi-stage build?
Short answerDocker packages an app with its runtime so it runs the same everywhere. Multi-stage builds compile in one image and copy only the output into a small final image.
How we used itAPI: install prod deps, run as non-root, HEALTHCHECK. Web: build with Node, serve static files with nginx.
Why industry uses itReproducible environments, smaller attack surface, standard unit for Kubernetes and cloud hosts.
Follow-upsImage vs container? · Why order COPY package.json before COPY . ? (layer caching) · Why not run as root?
How do you test a Node API?
Short answerUnit-test pure logic; integration-test HTTP behaviour through the real middleware stack; keep a few end-to-end tests.
How we used itnode:test for streak and scoring rules; supertest against createApp() for auth, validation and error shape.
Why industry uses itThe testing pyramid / trophy balances speed and confidence.
Follow-upsHow would you test DB flows? (mongodb-memory-server or test containers) · Mocks vs fakes? · What makes a test flaky?
How did you refactor a 1,199-line file without breaking it?
Short answerKept every URL and response shape, extracted by responsibility, and added tests at the HTTP boundary.
How we used itSame routes, same JWT format, same login flow; frontend needed only two small changes (auth on content calls, removed markActivity).
Why industry uses itBehaviour-preserving refactors behind tests are how teams pay down debt without big-bang rewrites.
Follow-upsStrangler-fig pattern? · How do you refactor with no tests? (characterisation tests first) · What would you split next?

Beginner
What it isDeclaring the shape of data once and parsing untrusted input against it.

Architecture decisions worth discussing

Why server-derived streaks?

Security thinking: trust boundaries and what the client can be allowed to claim.

Why a partial unique index?

Concurrency plus safe migration of existing data.

Why embed resources in boards?

Read pattern fits; caps protect the 16 MB limit; know when you would split them out.

Why sessionStorage and not cookies?

Honest trade-off: simpler, tab-scoped, but XSS-readable. Explain the refresh-cookie upgrade path.

Why request coalescing?

Cost control on a quota-limited API; a small idea with a real-world payoff.

What breaks at 10× traffic?

In-memory limits and cache, embedded arrays, synchronous streak reads. Have the answer ready.
